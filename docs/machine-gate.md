# 로컬 기계 실행 게이트

이 문서는 기존 `admission-bootstrap/v1` 계약을 설명합니다. 실제 파일의 필수
검증·출처·최신성·효과 예산을 연결하는 명시적 v2 구성은
[산출물 검증 게이트](artifact-gate.md)를 확인하세요. 기존 상태를 자동으로
변환하거나 v1에 새 검증 필드를 암묵적으로 허용하지 않습니다.
v2의 실제 상태를 읽어 명령을 준비하고 같은 원문으로 재시도하는 실행 도구는
[`policy-client`](policy-client.md)입니다. 이 클라이언트는 v1용이 아닙니다.

**상태: 로컬 실제 실행 12개 사례 통과.** 합성 초기 상태와
실제 네이티브 실행 파일의 loopback API를 확인했습니다. 확인한 범위와
아직 보장하지 않는 범위를 아래에 구분합니다. 커밋별 공개 검증 결과는
[Verify Actions](https://github.com/kimjooyoon/gooo-policy-studio/actions/workflows/ci.yml)에서 확인합니다.

이 게이트는 인증된 기계 주체가 서버에 보관된 요청 한 건을 현재 정책으로
판단하고, 허용된 경우 `pending`에서 `approved`로 바꾸는 API입니다. 작업마다
사람의 승인을 받는 절차는 없습니다. 실제 효과는 로컬 상태의 승인 전이
하나이며 구매·송금·외부 API 호출을 수행하지 않습니다.

## 권위 있는 초기 설정

[초기 설정 예제](../examples/automation-gate/bootstrap.json)는 합성 자료입니다.
스키마는 `policy-studio/admission-bootstrap/v1`이며 서버 정책 `policy`,
기계 주체 `principals`, 요청 `requests`를 제공합니다. 이 파일을 준비하는
로컬 관리자가 설정의 신뢰 주체입니다. 일반 API 호출자가 정책, 검토자,
요청 금액이나 팀을 제공하거나 덮어쓸 수 없습니다.

이 저장소는 **한 정책 version의 고정 구성**입니다. 정책·요청·기계 주체를
추가하거나 바꾸는 API, 정책 migration, 토큰 rotation·revocation 관리 API는
구현하지 않았습니다. ‘현재 정책·권한’은 실행 중인 서버가 로드한 권위 있는
snapshot을 뜻합니다. 관리자가 파일을 바꿔도 실행 중인 서버가 즉시 읽어
반영하지 않습니다. 관리자 재작성 후 재시작을 일반 설정 변경 절차로
검증한 것도 아니므로 설정 관리의 lifecycle은 이번 단위의 범위 밖입니다.

예제의 `svc-policy-engine`은 `platform` 팀의 활성 기계 주체이며
`enabled`와 `can_execute`가 모두 `true`입니다. 인증·실행 권한 확인은
Gooo의 선택 가능한 `active_reviewer` 규칙과 별개의 필수 경계입니다.
정책에서 그 규칙을 꺼도 폐기된 자격증명이나 실행 권한 없는 주체를
허용하는 근거가 되지 않습니다.

초기화는 각 요청에 `pending` 상태와 revision `1`을 부여합니다. 예제는
1,000,000원 한도 아래의 `req-export-1`(750,000원)과 한도 위의
`req-export-over-limit`(1,100,000원)을 포함합니다. 이 금액은 합성 요청의
정수 원 값이며 고객 업무나 비용 절감 실적이 아닙니다.

## 초기화와 실행

명령은 다음과 같습니다. 상태 디렉터리와 자격증명 파일은 새 경로를
사용합니다. 기존 상태나 토큰을 덮어써 초기화하는 경로를 두지 않습니다.
자격증명 파일은 새 상태 디렉터리 밖에 둡니다. 아래 예제는 같은 부모 아래에
서로 다른 경로를 사용합니다.

```sh
go build -trimpath -o bin/policy-gate ./cmd/policy-gate
mkdir -m 700 -p "$HOME/.local/state/gooo-policy-studio"
./bin/policy-gate \
  -init examples/automation-gate/bootstrap.json \
  -state "$HOME/.local/state/gooo-policy-studio/demo" \
  -token-file "$HOME/.local/state/gooo-policy-studio/demo.token"
./bin/policy-gate \
  -state "$HOME/.local/state/gooo-policy-studio/demo" \
  -addr 127.0.0.1:8090
```

예제는 주체가 하나이고 `token_sha256`가 빈 문자열입니다. 초기화 명령은
새 32바이트 무작위 값을 64자리 16진수 토큰으로 만들고 SHA-256 해시를
설정에 채운 뒤 상태를 만듭니다. 원문 토큰은 새 자격증명 파일에 **0600** 권한으로 보관하며
터미널에 출력하지 않습니다. 빈 해시는 익명 접근을 허용하는 설정이 아닙니다.
게이트에 저장하는 주체에는 원문 토큰 대신 소문자 64자리 해시가 필요합니다.

기계 클라이언트는 자격증명 파일을 읽어 `Authorization: Bearer <token>`
헤더로 인증합니다. 토큰을 URL, JSON 본문, 저장소, 공개 로그나 보고서에
넣지 않습니다. 자격증명 파일과 상태 디렉터리는 관리자가 보호해야 합니다.
기본 주소는 `127.0.0.1:8090`이며 명령은 리터럴 loopback IP에만 바인딩합니다.
외부 노출을 위한 TLS·프록시 배포는 이 로컬 구현의 검증 범위에 포함하지 않습니다.

운영 대상은 Linux와 macOS의 로컬 파일 시스템입니다. 현재 실제 로컬
12개 사례는 macOS에서 확인했으며 Linux 실행은 커밋별 공개 CI에서 확인합니다.
배타적 잠금과 파일·디렉터리 동기화를 지원하지 않는 환경에서는 시작이나
저장을 거절합니다. 네트워크 파일 시스템의 잠금·전원 장애 내구성을 검증하지
않았습니다. 지원하지 않는 잠금 플랫폼에는 대체 실행 경로를 두지 않습니다.

초기화 오류에도 자격증명 파일이 남을 수 있습니다. 상태 파일 교체 뒤 동기화가
실패했다면 상태도 이미 만들어졌을 수 있으므로 자동으로 지우거나 덮어써 다시
초기화하지 않습니다. 유지된 자격증명과 영속 상태를 확인하여 복구해야 합니다.

## API 계약

두 API 모두 Bearer 인증이 필요합니다. 쿠키, 출처 헤더, 저장된 시뮬레이션
기록이나 회귀 검사 보고서가 인증을 대신하지 않습니다.

| 경로 | 입력 | 반환 범위 |
| --- | --- | --- |
| `GET /api/state` | Bearer 헤더 | 현재 `policy_version`, 요청별 `request`·`status`·`revision`, 인증된 자기 `principal` |
| `POST /api/admit` | Bearer 헤더와 아래 네 필드의 정확한 JSON | 해당 명령에 연결된 승인 또는 거절 결과 |

`POST` 본문은 최대 4 KiB이며 `Content-Type: application/json`을 사용합니다.
`charset=utf-8`만 추가할 수 있습니다. Authorization 헤더는 하나여야 하며
Origin 헤더나 URL query가 있는 요청은 거절합니다.

승인은 `200`의 `{replayed, outcome}`으로 반환합니다. 실제 Gooo 거절은
`403`의 `{error: "policy_denied", result: {replayed, outcome}}`으로 반환하므로
인증·작업 권한 거절과 구분할 수 있습니다. 거절 결과도 `outcome.id`와 실행
기록을 포함합니다. `replayed: true`는 저장된 원래 결과를 다시 반환했다는
뜻이며 새 승인이나 정책 재판단을 뜻하지 않습니다.

상태 응답은 토큰 해시와 다른 주체의 설정을 공개하지 않습니다.
클라이언트는 상태 응답의 정책 version과 해당 요청 revision을 사용합니다.
아래 값의 version과 revision은 형태를 보여주는 예시이며 실제 상태에서
읽은 값으로 채워야 합니다.

```json
{
  "request_id": "req-export-1",
  "expected_revision": 1,
  "policy_version": "<GET /api/state에서 받은 값>",
  "idempotency_key": "export-admission-1"
}
```

네 필드는 모두 필수입니다. 누락·`null`·중복 키·이름의 대소문자 별칭·
알 수 없는 필드·잘못된 UTF-8 등 모호한 JSON을 거절합니다. `rules`,
`reviewer`, `request` 또는 임의 작업·URL·명령을 추가하여 실행 범위를
넓힐 수 없습니다.

## 판단과 원자적 상태 전이

게이트는 현재 서버 상태의 요청과 인증된 주체를 기존
[Gooo `Evaluate`](../policy/approval.gooo)에 전달합니다. 주체의 key·team·active가
검토자 입력이 되고 서버의 현재 정책이 규칙 입력이 됩니다. 제출, 검토자 활성,
자기 승인, 팀, 한도 판단을 Go나 HTTP 계층에서 다시 구현하지 않습니다.

정책 version은 정책 값과 실행 중인 Gooo 소스·생성 코드의 출처에 연결합니다.
실행 직전 현재 version과 요청 revision을 확인하고, 기대한 상태와 일치할
때만 그 상태에 대한 판단을 사용합니다. 단일 writer의 직렬화 경계 안에서
판단부터 저장까지 처리하므로 중간에 다른 승인 요청이 끼어들어 같은 revision을
소비할 수 없습니다. 이미 승인된 요청을 새 키로 다시 승인하지 않습니다.

Gooo가 승인하면 요청 revision을 증가시키고 `approved` 상태로 전이합니다.
거절하면 요청은 `pending`으로 남습니다. 두 경우 모두 명령·주체·정책 version·
실제 Gooo 실행 기록과 결과를 영속 idempotency 기록에 연결합니다.
`committed: true`는 승인 상태 전이가 완료됐다는 뜻이며, `false`는 해당
결과가 승인 전이를 수행하지 않았다는 뜻입니다.

요청 상태와 결과 기록은 **같은 원자적 상태 파일 교체**로 저장합니다.
임시 파일 기록·동기화, 교체, 디렉터리 동기화를 마친 뒤에만 완료를 반환하는
범위입니다. 프로세스 간 배타적 writer 잠금으로 같은 상태를 동시에 여는
두 writer를 허용하지 않습니다. 이 보장은 해당 잠금과 저장 규약을 따르는
로컬 프로세스 및 지원하는 파일 시스템에 한정됩니다.

시작 시 원문 JSON, snapshot의 내용 해시, 현재 실행 파일의 Gooo 소스·
생성 코드·어댑터·생성 근거·컴파일러 출처를 확인합니다. 저장된 모든 결과의
실행 기록을 기존 Gooo로 다시 계산하고 요청 상태와 이력의 일관성을 확인합니다.
위 Gooo 실행 출처가 바뀐 실행 파일로 기존 snapshot을 자동 수용하지 않습니다.

저장 규모는 기계 주체 **1~32개**, 초기 요청 **1~256개**, 승인과 거절을
합친 영속 결과 **최대 256개**, snapshot **최대 4 MiB**입니다. 결과를
eviction·압축·자동 삭제하지 않습니다. 결과 상한에 도달하면 새 명령은
`503 unavailable`로 거절하고 추가 전이를 수행하지 않습니다. 이미 보관한
동일 명령의 재시도는 상한 뒤에도 원래 결과를 반환합니다. 초기 JSON 입력은
최대 1 MiB입니다. CLI 초기화는 예제처럼 한 주체의 새 토큰 생성만 지원합니다.

## 재시도와 자동 실패 처리

idempotency key는 인증된 주체와 정확한 명령 내용에 연결됩니다. 동일한
주체·키·내용의 재시도는 저장된 원래 결과를 반환하고 다시 상태를 바꾸지
않습니다. 같은 키에 요청 ID·revision·정책 version 등 다른 내용을 넣으면
충돌로 거절합니다. 승인과 거절 결과 모두 재시작 뒤에도 이 경계를 유지합니다.

응답을 받지 못한 경우에는 원래 네 필드와 키를 유지해 재시도합니다.
현재 상태를 다시 읽고 기존 키에 새로운 revision이나 정책 version을 붙이는
것은 동일 명령의 재시도가 아닙니다. 서버가 로드한 주체의 `enabled` 또는
`can_execute`가 허용하지 않으면 과거 실행 결과도 반환하지 않습니다.
이는 실행 중인 서버에 외부 설정 변경을 즉시 전파하는 폐기 기능이 아닙니다.

| 조건 | 응답과 실패 처리 |
| --- | --- |
| 인증 실패, 로드된 주체의 `enabled: false` | `401 unauthorized`; 실행·실행 결과 반환 거절 |
| 로드된 주체의 `can_execute: false` | `403 forbidden`; 실행·실행 결과 반환 거절 |
| Origin·교차 출처·URL query | `403 MACHINE_CLIENT_REQUIRED`; 실행 거절 |
| 잘못된 JSON·호출자 override | `400 INVALID_COMMAND_JSON`; 승인 전이 없음 |
| JSON 미디어 타입·charset 불일치, 과대 본문 | `415` 또는 `413`; 승인 전이 없음 |
| 타입은 맞지만 명령 값·키·revision 범위가 잘못됨 | `422 invalid_input`; 승인 전이 없음 |
| 알 수 없는 요청, 현재 정책 version·revision 불일치, 이미 승인된 요청 | `409 conflict`; 승인 전이 없음 |
| Gooo 거절 | `403 policy_denied`와 저장된 결과; 요청은 `pending` 유지 |
| 같은 키에 다른 명령 | `409 conflict`; 기존 결과 덮어쓰기 없음 |
| Gooo 실행 오류, 유효하지 않은 상태·출처, 결과 상한 | `503 unavailable`; 추가 승인 전이 없음 |
| writer 잠금 실패 | 서버 시작 실패 |
| 저장 결과가 불확실한 I/O 오류 | `503 unavailable`; 해당 프로세스의 추가 작업을 중단하는 fail-stop |

쓰기·교체·동기화 도중 오류가 나면 승인 전이가 디스크에 남았는지 즉시
단정할 수 없습니다. 이런 오류를 일반 거절이나 성공으로 바꾸지 않으며,
메모리 상태로 실행을 계속하거나 새 키로 자동 재실행하지 않습니다.
재시작 시 유효한 영속 상태를 확인하고 동일 명령·키로 저장된 결과를 확인해야
합니다. 손상됐거나 실행 출처와 맞지 않는 상태에서 자동 초기화로 우회하지
않습니다.

## 보장하지 않는 범위

기존 유한 배치의 **PASS**는 제공된 사례의 기대값 일치입니다. 승인 영수증과
보고서의 해시는 내용 일관성과 재현성을 검사할 뿐 발행자를 인증하지 않습니다.
이들 파일을 가져와도 기계 실행 권한을 얻지 못합니다.

이 구현이 보장하려는 효과는 신뢰하는 로컬 상태의 승인 전이와 영속 중복
방지까지입니다. 외부 API의 정확히 한 번 실행, 구매·송금의 원자성, 조직의
누적 예산, 임의 입력에 대한 정책의 완전성을 보장하지 않습니다. 토큰 탈취나
로컬 관리자의 설정·상태 재작성도 방어 범위 밖입니다. 상태 해시는 관리자가
전체 상태를 일관되게 다시 쓰는 것을 인증상 구분하는 서명이 아닙니다.

실제 고객 자료나 고객 업무의 무인 운영 사례는 없습니다.

## 확인한 실행 근거

[실제 실행 확인 스크립트](../tools/verify-machine-gate.py)는 새 합성 상태와
새 자격증명을 만들고 실제 `policy-gate` 실행 파일에 loopback HTTP로 요청합니다.
프록시와 리다이렉트를 사용하지 않으며 토큰 원문이나 요청 인증 헤더를 증거에
보관하지 않습니다. 현재 로컬 관측의 사례는 다음 12개입니다.

- 자격증명 누락 `401`, 오래된 정책 `409`.
- 호출자 정책 override와 중복 JSON 키 `400`.
- 실제 Gooo 승인 `200`, 같은 명령 재시도에서 원래 승인 결과 반환.
- 같은 키의 변경 명령 `409`, 새 키로 오래된 요청 revision 사용 `409`.
- 한도 초과 실제 Gooo 거절 `403`.
- 두 번째 프로세스의 writer 잠금 획득 거절.
- 정상 종료 후 재시작에서 원래 승인·거절 결과 각각 반환.

최종 상태는 `req-export-1: approved/revision 2`,
`req-export-over-limit: pending/revision 1`입니다. 확인한 실행 파일의 SHA-256은
`6b8d11a08e49e91eb2832c3637067e0c221b698a4fa69e58876a447eda7daafc`입니다.
이 관측은 개발 중 로컬 실행의 근거이며 공개 CI의 정확한 커밋 검증 결과를
대신하지 않습니다. CI에서도 같은 실제 실행 검사와 결과 파일 보존을 수행합니다.

재시작 검사는 **SIGTERM에 의한 정상 종료**를 사용했습니다. 강제 crash,
SIGKILL, 전원 장애나 파일 시스템 손상을 실제로 재현한 검증은 아닙니다.
단위 테스트의 주입된 저장 오류 경로도 실제 전원 장애 검증을 뜻하지 않습니다.
